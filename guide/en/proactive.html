Finding threats that raised no alert, and writing the rules that would

Triage starts from an alert. What a SOC misses usually lives on the other side - behaviour no rule fired on, and the fact that no rule exists for it. The two entries under "Proactive detection" cover exactly that: Threat hunting searches the environment from one hypothesis; Detection engineering turns one threat into a rule draft.

Both rest on the same principle: the AI only reads. It creates no case, writes no comment, installs no rule. Those decisions are a person's; what the AI hands over is the grounds for them.

1. Threat hunting - one hypothesis to start

"A host is beaconing to the LokiBot C2", "someone created an external forwarding rule on an M365 mailbox". Write the hypothesis as one sentence, pick a window, and a run starts. It ends one of two ways.

  • Candidates - a table of the entities (hosts, users, addresses) that actually did the behaviour. Each row carries the search and count that showed it, and the entity's own 30-day baseline - "this host reached that domain" and "this host has reached it every day for a month" are different stories.
  • Not found - the list of what was searched, over which window, with which conditions, returning nothing. The word "clean" is never used. Zero means nothing matched those conditions in that window; it does not mean the environment is safe.

If the hypothesis needs a log this environment does not ingest, the hunt does not start searching and says so - "this log has to be ingested before this question can be answered". A zero from a source nobody sends means nothing.

Add an IOC list and the hunt becomes a sweep: every indicator is searched in every field its type can land in, and the ones found and the ones not found are tabled separately. Skipping an indicator from the list is an automatic failure.

From the hunt screen a candidate's pattern can be handed straight to a detection draft - the road from "why was there no alert" to a rule.

2. Detection engineering - one threat to a rule draft

Describe the threat and the AI takes five steps.

  1. Can we see it - first, whether this environment ingests the logs the behaviour would land in. If not, no rule is written. A rule that can never fire is not a smaller deliverable; it is a wrong one.
  2. Does a rule already catch it - the environment's rule list is read to the last page and compared. If one already catches it, the proposal is to tune that rule, not to add one. Similar rules that miss are listed with why each misses.
  3. The draft - the YARA-L rule text, with what it keys on and what would make it fire by accident (the look-alike benign process, the maintenance window, the service account).
  4. How often it would fire - counted, before anyone installs it, on this environment's last seven days of data. Each customer sets an alert budget (20 a day by default). Over budget, the draft is not finished: a threshold (one entity, more than N times in an hour), a named exclusion (the scanner or backup server on the allowlist), a narrower field - in that order, re-counted after each change. The numbers before and after stay in the report. If it cannot be brought under budget, it is handed over as over budget, with the number - never as quiet.
  5. Syntax validation - only a draft that compiled is "validated". Errors are shown verbatim.

The draft card shows these as pills: observable or not, existing coverage (gap / already caught), about N alerts a day · budget 20, validation N/M, and not installed. The rule text can be copied as is.

3. What it never does

  • It never installs a rule. A wrong rule floods the SOC or goes silent. Installing is a person's, after approval.
  • It never creates a case or writes a comment. A hunt's candidates are not alerts and get no verdict.
  • It never writes a number no tool returned. Candidate names and counts come from search results only; anything else is marked on screen in a red box.
  • It never invents a reputation. Without threat intelligence (GTI) it writes "reputation not available" and never reads a missing lookup as benign.

4. How it is verified

Like triage, hunting and detection engineering have answer keys - but the answer is not a verdict, it is a premise: can this environment see the behaviour, does a rule already catch it, is the planted signal found, is an absent indicator ever called "clean". Every run is checked against those mechanically, and only a condition run three times counts as a result. What the first runs actually caught - a "gap" declared after four pages of a seven-page rule list, a rule drafted for an unobservable behaviour, detection scope thrown away to reach zero alerts - is where today's procedure came from.

Summary

  • A hunt starts from a hypothesis and ends with candidates or not found. There is no "clean".
  • A rule draft goes observable → already covered → draft → how often it fires → syntax, and is not installed.
  • The alert budget is the customer's; a draft over it is tuned, or handed over saying so.
  • Both only read. The decisions are a person's.
