How can you trust what the AI concludes

When the AI says "this one is a false positive", you have to be able to act on it. If you cannot, an analyst investigates the case again from the start — and then the AI has not removed work, it has added a second copy of it.

So this product shows the grounds before the conclusion. Every number on the screen can be traced to the query that produced it, and numbers that cannot be traced are prevented from appearing at all. Here is how.

1. The events attached to an alert are a sample, not the evidence

The SOAR attaches a handful of sample events to an alert. A detection that fired on 1,000 downloads still arrives with ten. Reading those ten and writing "ten files, routine work" is how a real incident gets closed.

An investigation therefore counts the whole detection window again, separately from the sample the alert carried. When a query hits its page limit the screen says so — 3,000+ ⚠ page cap reached — which means every figure above it is a floor, not a total. Presenting a capped number as exact is how an analyst ends up reasoning with false precision.

2. Nothing is called unusual until it has been compared with usual

A real example. An account signed in successfully from Spain and from China six minutes apart — a physically impossible journey, on the most privileged account in the estate. Read only the two events inside the detection window and it is a breach.

Counting the same account's last 30 days showed sign-ins twice a day, every day, from the same two addresses. No attacker produces that regularity; it was the environment's own automation.

An investigation asks "is this entity new or recurring" and "what is this actor's normal volume" before it concludes. A verdict reached without that comparison loses points in our own scoring, and those runs are caught in review.

3. A number no tool returned cannot appear in the report

This is the most dangerous failure of generative AI, because a plausible invented figure cannot be recognised as invented by the person reading it.

Two layers stand against it.

  • The tool response warns about itself. When a list query returns one page, the response carries the sentence with it: this is a page and not a total, and the only figure you may report is "N or more".
  • Scoring catches it afterwards. Every investigation is stored together with its tool calls, and a separate check compares the figures in the report against what the tools actually returned. A mismatch is an automatic failure, whatever the rest of the score says.

4. We say what we can see before we say what we found

"Checked EDR, nothing found" is only true if that organisation sends EDR logs. Claiming to have checked telemetry that is not collected is the worst kind of error: it reassures with evidence that does not exist.

So each customer gets an inventory of the log sources actually arriving, and the investigation screen shows it alongside the report. Using telemetry outside that inventory as grounds is an automatic failure. For the gaps, the correct sentence is "we do not see this area" — and we write it.

5. The grounds are kept as they were, so a judgement can be reviewed later

A SIEM keeps changing. The same query returns something different next week. So for the cases we evaluate against, the grounds of the investigation are stored together as one set: the case, its alerts, the full rule text, the entities examined, and the results of the queries run inside the detection window.

Two things follow. A judgement can be reviewed months later against the evidence it was actually made on. And when the model or the procedure changes, "better or worse" can be measured under identical conditions — a comparison that does not hold conditions fixed is not a comparison.

6. A person decides anything that cannot be undone

Closing a case, isolating an account, blocking an address: the AI does not perform these. The action, its target and its grounds go onto one approval card, and it runs only when a person approves it. An approval button without the grounds beside it becomes a rubber stamp, which is why they are never separated.

Rejecting requires a reason. That reason is carried into subsequent investigations, so the same correction does not have to be made twice.

7. What we cannot do yet

Written plainly.

  • Cost figures are estimates. They are calculated from list prices, not read from an invoice. The screen always says "about".
  • The AI's verdict is not the final word. It still tends to state a conclusion when the evidence is thin, and we are steadily moving those cases towards "cannot determine — needs a person".
  • An accuracy figure is only meaningful with the data it was measured on. Accuracy on test data and accuracy in a live environment are different numbers. The one that belongs in a contract comes from an answer key built from that customer's own cases.

8. It works without threat intelligence (GTI)

Google SecOps Enterprise does not include Google Threat Intelligence, and most customers run Enterprise. So reputation lookups are built as use them when they exist, say so when they don't.

  • For a customer without GTI the lookup tools are not attached at all, and the AI is told first that this customer has no threat intelligence.
  • What remains as grounds: SecOps's own IOC feed, the entity's 30-day baseline, this customer's past cases, and what the rule keyed on. The report says "reputation not available".
  • Reading a missing lookup as benign is an automatic failure - it is in the answer key.
  • The coverage line on screen shows "No threat intel". Customers with GTI (Enterprise Plus) see no such mark, and reputation lookups join the grounds.
